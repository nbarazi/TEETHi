# TEETHi: End-to-End Test Report (2026-10-23)

**Scope:** all four platforms running together. A new dentist and a new patient were registered and set up from scratch, and one visit was taken through its whole life: booking, acceptance, documentation, completion, report, review and invoice. The admin dashboard was checked along the way. Edge cases were then probed directly against the API.

**Setup:**
- Backend on :8000 against local MySQL, with a queue worker. SMS and mail used the **log** drivers, so nothing was sent to a real phone or inbox.
- Patient app (:8917) and dentist app (:8765) ran as Flutter web debug builds at phone size (375×812).
- Admin dashboard on :4200. Stripe was in test mode.
- The machine is on UTC+3. The dentist is in Los Angeles; "today" there was Fri 23 Oct.

IDs below are new for this run (prefix **R8-**). Where a row matches an issue already in `CONSISTENCY_REPORT.md`, that ID is noted.

---

## 1. Summary

The core lifecycle works end to end: sign-up, verification, onboarding, booking with insurance and consent, accept, document, complete, then the patient gets the report, prescription, recommendation and invoice, and leaves a review. Server-side rules are solid in most places: slot conflicts, working hours, timezone validation, ownership checks, open-pool claim races and status transitions all behaved correctly.

The problems are concentrated in five areas:

1. **Trust and safety.**
   - Dentists can be booked before anyone has vetted them.
   - A penicillin-allergic patient was prescribed amoxicillin with no warning.
   - The dentist never sees the patient's medical conditions.
2. **Verification-code entry.** A bug in both apps can stop a user from completing sign-up.
3. **Notifications.** The dentist gets no notification when a patient books them directly.
4. **Data integrity.**
   - The patient profile form saves blood type, gender and title the user never chose.
   - Clinical records can be written on visits that never happened.
5. **Stale screens.** Several screens don't refresh, so both apps show out-of-date status.

## 3. Findings

### High

**R8-01: Unvetted dentists are bookable, and licence verification gates nothing.**
- **What happens:**
  - A brand-new dentist with no licence uploaded, no agreements signed and no admin review was listed to patients immediately (`GET /patient/providers?q=Layla` returned her a minute after sign-up).
  - She accepted, started and completed a visit while her licence was still "awaiting review".
  - The dentist app promises "We check your licence before your first request", and the patient onboarding says "Licensed dentists across Los Angeles".
  - Admin verification (`LegalDocumentService::verify`) exists, but nothing reads the result.
- **Where:**
  - `Patient\ProviderController::index` filters only on `user.status = active`.
  - Nothing in `RequestController` (accept/start) or `BookingService` checks for a verified licence or signed agreements.
- **Fix:** add a "bookable" state that needs a verified, unexpired licence and insurance plus both signed agreements. Filter the directory and open-pool notifications by it, and block accept until it's met.
- **Fixed (2026-10-24, backend):**
  - `DoctorProfile::isBookable()` / `scopeBookable()` require a verified, unexpired license and liability insurance plus a signed copy of every currently active business agreement and nondiscrimination notice.
  - `GET /patient/providers` lists only bookable, active doctors; new-open-request notifications fan out only to bookable, active doctors.
  - A direct booking naming a non-bookable doctor is `422` on `doctor_profile_id` (`booking.doctor_not_bookable`); accepting a request as a non-bookable doctor is `409` with the same message.
  - Credential uploads now also write the declared `expiration_date` to `legal_documents.expires_at`, and the doctor dashboard flags a required re-sign when an agreement template version is replaced.
  - **Tests:** `tests/Feature/Api/V1/Doctor/BookabilityTest.php` covers the criteria, directory filter, direct-booking rejection and re-sign flag; request/notification tests cover the accept gate and fan-out. Full backend suite passes (637).
  - **Review follow-ups (2026-10-24, same change):**
    - **Demo seed:** new `DoctorCredentialSeeder` (runs last in `DatabaseSeeder`) signs the active agreements and uploads and verifies a licence and insurance for the 8 demo dentists through `LegalDocumentService`, so a fresh seed has a full directory. Safe to re-run.
    - **Profile, reviews and slots gated:** `GET /patient/providers/{doctor}`, `…/reviews` and `/patient/availability` are `404` for a doctor who isn't listed (`DoctorProfile::isVisibleToPatient()`), except for a patient who already has a live visit with them, so it can still be rescheduled.
    - **Dentist told why:** `GET /doctor/dashboard` adds `bookable` and `bookability_gaps` (`not_uploaded`, `awaiting_review`, `rejected`, `expired`, `not_signed`) from `DoctorProfile::bookabilityGaps()`, which `isBookable()` now uses. Agreement templates are filtered to doctor audiences, matching the re-sign banner.
    - **Expiry backfill:** migration `2026_10_24_000001_backfill_credential_expires_at` copies `metadata.expiration_date` into `expires_at` where it was empty.
    - **Renewal keeps the dentist online:** uploading a new licence or insurance no longer retires the verified one. The old one stays in force until the renewal is verified (then it becomes `superseded`), and stays if the renewal is rejected. A dentist only drops out if the old credential actually expires first. 5 tests in `BookabilityTest`.
    - **Tests:** 16 more in `BookabilityTest` (24 total); two `ProviderTest` cases now use a bookable doctor. Full suite 653 passing, PHPStan and Pint clean.
    - **Live (local DB, migration and seeder applied):** directory lists all 9 dentists; an incomplete profile is `404` for detail and slots; an unvetted dentist's dashboard lists all four gaps.
  - **Still open:** the admin queue now names the dentist (R8-19, fixed 2026-10-25). The dentist app doesn't show `bookable` / `bookability_gaps` yet, and the patient app doesn't yet handle the new `404` on a dentist's profile.

**R8-02: No allergy safety when prescribing, and medical conditions are hidden from the dentist.**
- **What happens:**
  - The patient recorded *Penicillin, Latex* allergies and *Type 2 diabetes*. The dentist prescribed **Amoxicillin 500mg** with no warning.
  - The visit-documentation screen doesn't show allergies at all.
  - The dentist's patient chart shows allergies and medication but **not conditions or notes**, although the API sends them (`GET /doctor/patients/{id}` → `medical_history.conditions`).
- **Where:** `TEETHI-Dentist-App/lib/features/patients/data/mappers/patient_mapper.dart` maps `allergies` and `current_medications` only.
- **Fix:**
  - Show conditions and notes in the chart.
  - Put an allergy and conditions banner at the top of the visit workflow.
  - Warn (at least on a simple name match) when a prescription mentions a listed allergen.

**R8-03: Direct bookings never notify the dentist.**
- **What happens:**
  - Booking with a chosen dentist created no notification for her.
  - Her notification list was empty until the patient later cancelled or messaged.
  - Only open-pool requests notify dentists.
- **Where:** `TEETHi-Backend/app/Services/BookingService.php:153-165`. The `Direct` branch creates the conversation and invoice but never calls the notification service.
- **Fix:** notify the doctor (database and push) for new direct requests and for patient-initiated reschedules.

**R8-04: Code entry (both apps): "Clear", and moving from the email step to the phone step, leave the old digits in the hidden field.** ✅ **Fixed 2026-10-24:** dentist app `c0ceb52`, patient app `22be409` (both fast-forwarded to `master`). See the note at the end of this entry.
- **What happens:**
  - The six boxes are drawn from widget state, but the hidden `TextField` has no controller. "Clear" and the email-to-phone transition reset the boxes but **not** the field.
  - With `maxLength: 6` the field is already full, so new digits are silently dropped. The boxes stay empty and the CTA keeps saying "Enter the six digits".
  - Reproduced:
    - Dentist app: after "Clear", and on "Confirm your mobile", the hidden field still held the email code.
    - Patient app: wrong code → Clear → retype.
  - The only way out is invisible backspacing or reloading the app.
  - After a "Resend code", the old digits also stay in the boxes.
- **Where:** `CodeEntryField` in `TEETHI-Dentist-App/.../auth_screens.dart:790` and `TEETHi-Patient-App/.../auth_screens.dart:615`. The `VerifyScreen` is reused through `didUpdateWidget`.
- **Fix:** give `CodeEntryField` a `TextEditingController` and `FocusNode` owned by the screen. Clear it on Clear, on resend and in `didUpdateWidget`, and refocus it. Tapping the boxes should request focus.
- **Fixed (2026-10-24):**
  - `CodeEntryField` is now stateful and owns the controller and focus node. It takes `code` whenever the parent changes it and refocuses after a reset, so Clear, resend and the email-to-phone step all empty the hidden field.
  - The patient booking step's "Resend code" now also clears the old digits.
  - **Tests:** `test/widgets/code_entry_field_test.dart` in both apps (4 tests). Three of them fail against the old widget with the live symptoms; both full suites pass (dentist 155, patient 109).
  - **Live (dentist app, password reset):** after Clear, the field is empty and a new code fills the boxes.
  - **Still open, web + mouse only:** after *clicking* Clear, the cursor doesn't return by itself (the browser moves focus away on mousedown), so the user taps the boxes once before typing. Not seen with touch.

**R8-05: The patient profile form saves Title, Gender and Blood type the user never chose.**
- **What happens:**
  - Opening "Edit profile" pre-selects **Mr / Male / O+** when those are empty. Saving only a date of birth wrote `title: Mr`, `gender: male`, `blood_type: o_positive` to the record, and the dentist sees them as medical facts.
  - The avatar initials then changed from "ON" to "MO", built from "Mr Omar".
- **Where:** `TEETHi-Patient-App/lib/features/profile/presentation/screens/profile_screen.dart:583-585` (defaults), and `:545` (falls back to `oPositive`).
- **Fix:** default to "not set", and only send fields the user changed. Build initials from first and last name.

**R8-06: Clinical records can be written on visits that never took place, and visits can be started a day early.**
- **What happens:**
  - The API accepted `visit-outcome`, `clinical-notes` and `prescriptions` (201) on a **pending** visit, and again after it was **declined**.
  - The prescription then appears in the patient's records.
  - In the app, "Start visit" worked 26 hours before the scheduled time, and the visit was completed that same day.
  - The admin list shows a "Completed" visit dated tomorrow, with no flag.
- **Where:** `routes/api/v1.php:249-257`. The controllers authorize ownership but not appointment status.
- **Fix:**
  - Allow these writes only while the visit is `in_progress`; allow `completed` only for later additions within a short grace period.
  - Allow start only within a window around `scheduled_at` (for example 2 hours before).

**R8-07: A patient can book a dentist for a service she doesn't offer.**
- **What happens:**
  - The API accepted Braces ($8,000) booked with a general dentist who listed only preventive services.
  - The app sends only **one** of the selected `treatment_id`s to the provider search (`treatment_id=2` for Checkup + Fluoride), so mismatched dentists can show up.
- **Fix:** validate in `StoreAppointmentRequest` that every treatment is in the doctor's active expertise. Send all selected treatment ids to the provider search.

**R8-08: Payments.** (environment issue first, then app behaviour)
- **The local database was missing the merged Stripe migration.**
  - `2026_10_22_000002_add_stripe_payments` was still pending, so card payment returned **500**: `Unknown column 'stripe_customer_id'`.
  - **I applied it locally** (`php artisan migrate`; additive, reversible).
  - Add "run migrations" to the merge checklist and the deploy step.
- **Orphaned Stripe customer.** The Stripe customer was created *before* the failing database write, which left an orphan test customer.
- **Payment attempts after card then "Pay later".** Choosing card and then "Pay later" left three payment rows: `failed`, an `initiated` PaymentIntent that was never cancelled, and `pay_later`. Cancel or void the abandoned PaymentIntent when the method changes.
- **Confusing copy on the payment step:**
  - "Due today $180" sits right under "Estimated coverage ≈$72".
  - "Nothing is taken until the dentist confirms" sits next to a "Pay $180" button.
  - The terms checkbox is **pre-ticked**; consent should be opt-in.
  - Apple Pay ("Face ID") is offered on web and Android.
- **Wrong confirmation copy.** The confirmation says "Your appointment is scheduled" while the visit is `pending` until the dentist accepts.

**R8-09: Signing into the wrong app leads to a dead end.**
- **What happens:**
  - The dentist's account logged into the **patient** app successfully.
  - Home said "Your account type does not have access", and Profile showed only "Retry", with **no way to sign out**.
  - Neither app checks `user.role` after login. Both auth data sources set the role only when registering.
  - Found live in the patient app; the dentist app has the same code path.
- **Fix:** after login, reject a mismatched role with "This is a dentist account — use TEETHi for Dentists", and don't store the token.
